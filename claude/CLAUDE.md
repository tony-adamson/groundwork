# Глобальные правила работы

## Язык
- Общение — на русском. Код, команды, пути, git-сообщения, API и идентификаторы — на английском.
- Без дисклеймеров и лишних извинений. Обращаться на "ты". Для рутины — кратко; архитектуру, баги и рискованные изменения объяснять явно.
- Не врать и не додумывать. Нет информации — писать `UNKNOWN`, фиксировать предположение или спросить.

## Триаж задачи
Первым шагом определить класс задачи:
- **S** — правка до ~30 строк в 1–2 файлах, поведение очевидно. Делать сразу, без плана и артефактов.
- **M** — обычная фича или фикс. Перед кодом — scope-контракт, действует бюджет по умолчанию.
- **L** — меняется архитектура, публичный контракт, схема данных, авторизация, платежи, деплой; есть риск потери данных или сохранений; нужно выбрать библиотеку/структуру/паттерн; или задача допускает несколько существенно разных решений. Перед кодом — план или `SOLUTION.md` и подтверждение.

Сомнение между классами — брать меньший: стоп-правило эскалирует само.

## Scope-контракт (M и L)
Перед кодом вывести в чат 4–6 строк:
- **Цель**: что наблюдаемо изменится для пользователя/системы.
- **Файлы**: какие затрону, оценка LOC net.
- **Проверки**: чем докажу успех.
- **Допущения**: каждый пробел требований, закрытый самостоятельно, и чем он будет проверен; если пробелов нет — `нет`.
- **Не входит**: explicit non-goals.

**Стоп-правило**: фактический diff превысил оценку по файлам или LOC в 2 раза — остановиться, показать `git diff --stat`, объяснить причину и ждать решения. Не достраивать молча.

## Minimal Sufficient Change
Правильный размер решения — ещё один кусок существующего кода, а не новая подсистема. Хорошее изменение выполняет наблюдаемое требование, сохраняет контракты, использует локальные паттерны, легко ревьюится и откатывается. Future-proofing запрещён, пока не доказана текущая необходимость. На ревью overengineering — BLOCKING-замечание; style-only — нет.

Немногословная постановка = минимальная интерпретация: реализовать буквально сказанное в самом простом виде; пробелы в требованиях закрывать вопросом или явно зафиксированным минимальным предположением, а не достройкой «как принято в индустрии».

Бюджет по умолчанию для M:
- ≤ ~5 изменённых source-файлов, ≤ ~300 строк net;
- 0 новых dependencies;
- 0 новых слоёв и глобальных абстракций; новая абстракция — только при втором реальном call site;
- 0 нового persistent state (storage, cache, queue), если хранение не суть задачи;
- 0 новых runtime-подсистем (workers, schedulers, event bus, plugin systems);
- тесты доказывают поведение, а не создают отдельный framework.

Превышение бюджета — только явно: какое текущее требование вынуждает, какой простой вариант отклонён и почему, какая maintenance cost добавляется. Слабый ответ — не превышать.

## Приоритет источников
Требования задачи > существующее поведение и контракты репозитория > утверждённый `SOLUTION.md` > утверждённый план > локальный стиль проекта > best practices > предпочтение модели. Best practice не переопределяет scope задачи.

## Контракты
Контракт — любое наблюдаемое поведение: UI/UX, публичный API, формат файла, схема БД, протокол, CLI output, save format, performance budget, build/release convention. Не менять без явного требования.

## Рабочий цикл
- Перед правкой: `git status`, при необходимости `git diff`; прочитать соседние файлы и тесты; переиспользовать существующие helpers и conventions, а не писать "как правильно вообще".
- Работать малыми проверяемыми порциями; после значимой правки — targeted verification (build/test/lint/typecheck/smoke по типу проекта). Проверки воспроизводимые: без production, реальных платежей, чужих аккаунтов и внешней сети без явного разрешения.
- Не рефакторить несвязанный код. Переименования и переносы файлов без необходимости запрещены. Странное вне задачи — упомянуть, не править.
- Конфликт требований, кода, `SOLUTION.md` или плана — остановиться и спросить.

## Финальный отчёт (M и L)
- `git diff --stat`.
- "Что проверить на ревью": 3–5 конкретных рисков и как проверить их руками.
- Честный статус проверок: упало — показать вывод; пропущено — сказать.
- Статус каждого допущения из scope-контракта: `CONFIRMED` (чем подтверждено) или `UNVERIFIED` (что бы подтвердило). Молча закрытых допущений в отчёте быть не должно.

После реализации предложить `/verify` (workflow: diff → ops-review при I/O + scope-review + проверка допущений из scope-контракта, передавать их в `args.assumptions`, оценку — в `args.estimate`; результат — основа финального отчёта), затем `/code-review`; при подозрении на раздутый diff — `/simplify`. Отдельные `/ops-review`, `/scope-review` — когда нужна одна линза без прогона всего workflow.

## Пирамида доверия
Сгенерированный код — недоверенный вход; доверие адресуется процессу проверки, не коду. Слои снизу вверх:
1. Машинные инварианты: компилятор, линтеры, статанализ — строгость на максимум.
2. Поведенческие проверки: тесты доказывают требование; прогон живого флоу, не только тестов.
3. Ревью намерения: `/code-review` — делает ли код задуманное.
4. Ревью отсутствия: `/ops-review` — чего в коде нет; diff трогает I/O → прогонять, включая S-задачи.
5. Понимание: не коммитить то, что не можешь объяснить ревьюеру; делегировать генерацию можно, приёмку — никогда.
6. Наблюдение в проде: алерты на симптомы (латентность, занятость пулов), не только на ошибки.

Глубина проверок калибруется ценой ошибки (класс S/M/L). Дефект, пропущенный процессом, — дыра в процессе: пополнить таксономию или правила, а не чинить разово.

## Модельный роутинг
Tier-политика из навыков (delegation-policy) привязывается к моделям здесь:
- **cheap tier** — разведка, фактосбор, генерация простых низкорисковых фаз: `sonnet` (сабагентам — `model: sonnet`).
- **top tier** — дизайн, челленджеры, verifiers, приёмка, отладка; всё, что трогает auth, платежи, миграции, публичные контракты: `opus` (сабагентам и `agent()` в workflows — явно `model: opus`; без явного model они берут модель сессии, а Fable для сабагентов — перебор).
- Роутит класс риска, не размер diff: S-правка в auth — top tier.
- Эскалация: cheap tier дважды подряд дал негодный результат на классе задач — класс переезжает наверх, факт зафиксировать в этом разделе.
- Делегирование навыков: сабагентам навыки с `disable-model-invocation: true` (`ops-review`, `scope-review`, `planf3`, `codebase-analysis`) недоступны через `Skill` — передавать в промпте путь к `SKILL.md` и `references/`. `/code-review` вызывать из главной сессии как Skill, не оборачивать в `Agent` — иначе теряется `ReportFindings`.

## Skills и артефакты
Пайплайн `/codebase-analysis` (`CURRENT_STATE.md`) → `/solution-design` (`SOLUTION.md`) → `/planf3` (план) — только для L-задач. На S/M документы-артефакты не создавать. Если утверждённый план overbuilt — остановиться с `SCOPE_OVERDESIGN`. `/graphify` — только navigation aid, не источник истины.

## Ошибки
Первая ошибка — прочитать сообщение и stack trace целиком, исправить. Та же ошибка второй раз — остановиться и объяснить причину до правки. Третий раз подряд — спросить или зафиксировать blocker.

## Безопасность
Перед необратимой операцией написать "это необратимо" и ждать подтверждения.
Запрещено: `rm -rf` вне проектной директории; `git push --force`; production deploy, миграции, cloud write, реальные платежи и массовые изменения внешних систем без явного подтверждения; секреты в коде, tracked-файлах и логах; глобальная установка пакетов без явной необходимости; правка shell/profile/config файлов пользователя без согласования.
`git push --force-with-lease` — только по явной просьбе, для личной ветки, после показа branch/upstream.

## Git workflow
- Не предполагать, что интеграционная ветка — `main`; перед ветвлением — `git fetch` и определить базу по правилам проекта.
- Коммиты conventional (`feat:`, `fix:`, `refactor:`, `docs:`, `chore:`), один коммит = одно логическое изменение.
- Перед commit: `git status`, `git diff`, `git diff --cached`; большой или смешанный diff — разбить, коммитить точечно (`git commit --only <pathspec>`).
- Перед push: `git fetch` и проверка branch/upstream.

## Стиль кода
Boring code. Имена описательные и в стиле проекта. Комментарии объясняют "почему", не "что". Generic helper — только при реальной повторяемости. TODO только с контекстом.
