# Правила тестов

Источник — В. Хориков, «Принципы юнит-тестирования» (2020), страницы в скобках. Файл читают двое: модель, которая пишет тесты до реализации, и `scope-review` (п. 9). Тавтология и независимое ожидание — уже в п. 9, здесь не повторяются.

Наблюдаемое поведение — то, что видит клиент кода: возвращаемое значение, итоговое состояние, побочный эффект за границей приложения. Всё остальное — детали реализации, тест на них ломается при рефакторинге без бага (с. 93, 125).

## Моки

Управляемая зависимость — внепроцессная, но доступна только через это приложение: своя БД, свой кеш. Неуправляемая — её эффект видят другие системы: внешний HTTP API, платёжный шлюз, SMTP, шина сообщений, таблицы БД, которые читает другой сервис (с. 224–226).

1. Мокай только неуправляемые зависимости. Управляемую используй настоящей (с. 225, 254).
   Признак: `patch`/`Mock` на репозитории, сессии ORM, собственном сервисе или доменном классе.
2. Не проверяй вызовы стабов. Стаб отдаёт данные, вызов к нему — не результат (с. 121, 153).
   Признак: `assert_called*` / `verify` на методе, который возвращает значение и ничего не меняет.
3. Мокай последний тип перед внешней системой и проверяй payload, который уходит наружу, а не вызов своей обёртки (с. 257–260).
   Признак: `mock_notifier.send_email_changed.assert_called_once()` вместо проверки тела запроса к HTTP-клиенту/SMTP.
4. Проверяй и ожидаемые вызовы, и отсутствие лишних (с. 265).
   Признак: проверка «вызван хотя бы раз» без числа вызовов и без проверки остальных вызовов мока.
5. Мокай только свои типы. Над SDK стороннего сервиса — тонкий адаптер, мок — на адаптер (с. 265–266).
6. Число моков в тесте равно числу неуправляемых зависимостей операции. «Один мок на тест» — не правило (с. 264).

## Какой код каким тестом

| Код | Тест |
|---|---|
| Доменная логика, алгоритм: сложно или важно, мало зависимостей | юнит-тесты, все граничные случаи |
| Контроллер, handler, сервис-оркестратор: просто, много зависимостей | интеграционный: один самый длинный happy path через все внепроцессные зависимости + граничные случаи, которые юнитом не покрыть |
| Тривиальный: геттер, конструктор, проброс параметров | не тестировать |
| Сложно и много зависимостей одновременно | сначала разделить на логику и оркестрацию; тест на смесь — находка |

(с. 183–186, 220–222)

7. Не пиши тест на тривиальный код (с. 185, 201).
8. Не пиши интеграционный тест на ошибку, которая сразу роняет операцию (fail fast, нарушенное предусловие). Предусловие проверь юнит-тестом там, где оно объявлено (с. 222–223).
9. E2E — только для самого критичного пути, когда интеграционный тест не даёт той же защиты (с. 113, 229).

## Связь с деталями реализации

10. Не проверяй порядок и число внутренних вызовов, внутренние коллекции, текст SQL (с. 96, 108).
11. Не открывай приватное ради теста: `public`, геттер на приватное поле, флаг `if is_test:` в рабочем коде, `virtual`/`CallBase` для частичного мока. Тестируй через то, что читает рабочий код (с. 301–305, 308–312). Это же — п. 1 scope-review («для тестируемости» не обоснование).
12. Время, random, uuid передавай явно (параметр, значение из контроллера), а не глобальным патчем модуля (с. 313–315).

## Анатомия

13. Один тест — одна единица поведения: arrange, один act, assert. Несколько act подряд — только в медленном интеграционном тесте, где состояние дорого воссоздать (с. 67, 240–241).
14. В тесте нет `if` и циклов с логикой выбора (с. 67–68).
15. Act в одну строку. Если цели клиента нужны два вызова SUT подряд — вероятно, API раскрывает детали реализации (с. 68–70, 128).

## Тесты с БД

16. Та же СУБД, что в проде (версия может отличаться). SQLite in-memory вместо Postgres — нет (с. 287).
17. Arrange, act и assert — в разных сессиях/транзакциях. Одна транзакция на весь тест с `ROLLBACK` в конце расходится с продом (с. 283–284).
18. Очищай данные в начале теста, справочные данные не трогай (с. 285–286).
19. Состояние после act читай отдельным запросом в assert — для управляемой БД это законная точка проверки интеграционного теста, не побочный канал (с. 231).
20. Репозиторий отдельно не тестируй, он проверяется в интеграционных тестах операций. Чтения тестируй выборочно, записи — тщательно (с. 294, 296).

## Severity в scope-review

- BLOCKING: правило 11 (рабочий код изменён только ради теста) — как п. 1.
- WARN: правила 1–5, 7–10, 12, 16–17.
- INFO: правила 13–15, 18 — стиль, не блокирует.
